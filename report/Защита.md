Из каталога `program`:


## Что исправлено на финальной проверке

Динамические буферы и схема из трёх pipe уже были реализованы. Финальные исправления касались обработки ошибок:

- Добавлена проверка `waitpid` перед использованием статуса ребёнка; при `EINTR` ожидание повторяется.
- При `EINTR` повторяется прерванная запись `write`.
- `SIGPIPE` игнорируется: обрыв канала позволяет получить и сообщить `EPIPE` вместо молчаливого завершения сигналом.
- Добавлен `fflush(stdout)` родителя, чтобы результат появился сразу и выявлялась ошибка сброса вывода.
- Ошибка `getline` отличается от штатного EOF проверкой `feof`, включая случай неудачного выделения памяти.
- На ошибках создания каналов и первого fork закрываются уже открытые каналы; проверяются закрытия основных рабочих дескрипторов.

Вся логика родителя остаётся в одной функции `main`. Алгоритм обработки не изменён. Более ранние ошибки с фиксированным буфером, табуляциями вместо пробелов и неверным `printf` были исправлены до этой финальной проверки.

## Как работает программа

Родитель создаёт три трубки и двух детей. Первый ребёнок после `fork` запускает программу `child1`, второй — `child2`. Родитель читает строку, отправляет её первому ребёнку, получает готовую строку от второго и выводит. Дети не читают клавиатуру: их стандартные потоки перенаправлены на pipe.

```text
parent --pipe1--> child1 --pipe2--> child2 --pipe3--> parent
          ↑                  ↑                 ↑
       исходная           uppercase       один пробел
        строка                            вместо серии
```

Для каждого pipe писать нужно в `[1]`, читать — из `[0]`. `dup2` связывает номера 0 и 1 ребёнка с нужными концами каналов. Первый ребёнок читает из pipe1 и пишет в pipe2. Второй читает из pipe2 и пишет в pipe3. При EOF родитель закрывает pipe1, дети завершают чтение, выходят, родитель дожидается их.

Если последняя строка не содержит `\n`, родитель закрывает pipe1 до чтения результата: иначе первый ребёнок будет ждать конец строки, а родитель — ответ. Для длинной строки `write` может передать только часть байтов, поэтому родитель продолжает запись с оставшегося места. Дети читают всю строку в растущий буфер, что позволяет передавать строку больше ёмкости pipe.

## Вопросы на защите

**Что такое процесс?** Работающий экземпляр программы: у него есть PID, своё адресное пространство, состояние и открытые файловые дескрипторы.

**Что делает fork()?** Создаёт дочерний процесс. Родитель получает PID ребёнка, ребёнок — 0; при ошибке возвращается -1. После вызова оба продолжают выполнение, но идут в разные ветки условий.

**Что делает exec()?** Заменяет выполняемую программу внутри текущего процесса. PID сохраняется. Успешный `execl` не возвращается; возвращение означает ошибку.

**Что делает pipe()?** Создаёт однонаправленный канал — поток байтов, по которому процессы могут обмениваться данными. Возвращает через массив два дескриптора. Границы отдельных `write` читателю не обещаны.

**Почему [0] читает, а [1] пишет?** Так определён интерфейс функции `pipe`. Эти индексы массива не равны номерам stdin/stdout: например, фактические дескрипторы первого pipe в трассировке — 3 и 4.

**Что такое файловый дескриптор?** Номер открытого объекта ввода-вывода в конкретном процессе. Сам номер не содержит данные строки; через него ядру говорят, откуда читать или куда писать.

**Что такое stdin/stdout?** Стандартные потоки ввода и вывода. Их обычные номера: stdin — 0, stdout — 1; stderr для ошибок — 2. `stdin` как объект библиотеки C имеет тип `FILE *`, а `STDIN_FILENO` — номер 0.

**Что делает dup2(oldfd, newfd)?** Делает `newfd` ещё одним дескриптором того же открытого объекта, что и `oldfd`, закрыв прежний `newfd`, если нужно. Байты он не копирует. После `dup2(pipe1[0], 0)` чтение из stdin первого ребёнка идёт из pipe1.

**Зачем close()?** Закрывает ненужную копию дескриптора. EOF на канале появится после закрытия всех концов записи и чтения оставшихся данных. Лишний открытый конец записи может помешать EOF и вызвать ожидание навсегда.

**Зачем waitpid()?** Чтобы дождаться конкретного ребёнка, получить его статус и забрать сведения о завершении, не оставляя процесс зомби. Здесь родитель ждёт обоих детей.

**Как взаимодействуют процессы?** Parent пишет pipe1[1]; Child1 читает pipe1[0], делает uppercase и пишет pipe2[1]; Child2 читает pipe2[0], сжимает пробелы и пишет pipe3[1]; parent читает pipe3[0].

**Как реализована произвольная длина?** Фиксированного массива нет. `getline` выделяет и при необходимости увеличивает память; дальнейшая работа использует возвращённую длину. Реальный предел — доступная память и представимые размеры.

**Что такое getline?** Функция POSIX, которая читает целую строку из `FILE *`, включая `\n`, если он есть, и добавляет `\0`. Возвращает число прочитанных байтов без `\0`, либо -1 при EOF или ошибке.

**Зачем &buffer?** Функция может выделить или переместить буфер. Ей нужен адрес переменной-указателя, чтобы записать в неё новый адрес памяти. `buffer` имеет тип `char *`, `&buffer` — `char **`. В нашем коде буфер называется `line`.

**Что такое capacity?** Вместимость выделенного буфера в байтах. Это не фактическая длина строки. Например, под строку из 25 байтов может быть выделено 120 байтов. `&capacity` позволяет функции сообщить новый размер.

**Зачем free()?** Освобождает выделенную динамическую память после окончания работы с буфером. Вызов `free(NULL)` допустим.

**Что означает #define _POSIX_C_SOURCE 200809L?** Это настройка заголовочных файлов: включить объявления функций стандарта POSIX 2008. Она нужна для `getline`, `fdopen`, `sigaction` в строгом режиме C11. Это не переменная и не длина буфера.

**Зачем strace?** Чтобы увидеть реальные обращения к ядру: создание каналов/процессов, перенаправление потоков, передачу байтов, закрытие дескрипторов и ожидание детей.

**Что означает strace -f?** Следить также за дочерними процессами, созданными наблюдаемым процессом.

**Почему clone/execve/wait4?** В исходнике используются функции библиотеки C, а strace показывает системные вызовы ядра. На этой Ubuntu функция fork реализована через clone, execl — через execve, waitpid — через wait4. Кроме того, pipe показан как pipe2, dup2 — как dup3 с флагами 0. Это не означает изменения схемы программы.

**Почему fflush?** `fwrite` может только положить данные в буфер библиотеки. `fflush` отправляет их в канал сразу, иначе следующий процесс может ожидать данные, пока предыдущий ждёт новую строку.

**Какие ограничения у toupper?** Текущий алгоритм побайтовый и проверен на латинских буквах ASCII. Он не делает Unicode-преобразование регистра русских букв в UTF-8. Child2 сжимает именно обычные пробелы, не табуляции.

## Шпаргалка на 1–2 минуты

```text
parent → pipe1 → child1 → pipe2 → child2 → pipe3 → parent
                 UPPERCASE        сжатие пробелов
```

1. Три отдельные программы, два ребёнка, три однонаправленных pipe.
2. `fork` создаёт процесс; `exec` заменяет его программу.
3. `[0]` — читать, `[1]` — писать; это индексы массива.
4. Дескриптор — номер открытого объекта, а не строка данных.
5. stdin = 0, stdout = 1, stderr = 2.
6. `dup2` перенаправляет stdin/stdout ребёнка на нужные pipe.
7. `close` убирает лишние концы; без этого можно не получить EOF.
8. `getline(&line, &capacity, stdin)` сам растит буфер; возвращает реальную длину.
9. `capacity` — выделенная память; `&line` нужен для изменения указателя; `free` освобождает память.
10. Частичный `write` продолжаем; `fflush` сразу отправляет результат.
11. При EOF закрываем вход и вызываем `waitpid` для обоих детей.
12. `strace -f` наблюдает всю цепочку; clone/dup3/execve/wait4 — реальные вызовы ядра этой Linux-системы.
